# RBAC 권한 체계 (역할·상태·권역)

> 승인: 2026-11-12. 원본 요구사항은 제품 책임자와 합의한 "안심클린 매니저 앱 RBAC 권한 시스템 구축" 문서이고,
> 그 문서의 결정 사항 + 1·2단계 질의응답(아래 §15)을 합친 것이 이 문서다.
> **권한 규칙은 이 문서가 유일한 기준이다.** `BACKEND_PLAN.md` §3-8, `CLAUDE.md` §11-8 은 이 문서를 가리킨다.
> 결정을 바꾸려면 먼저 사용자에게 묻고, 이 문서 §15 에 날짜와 함께 적는다. 임의로 완화하지 않는다.
> 구현 진행 상황은 §14 표와 `PROGRESS.md` "RBAC" 절. 아직 구현하지 않은 규칙은 §14 에서 "예정" 이다.

---

## 1. 기본 원칙

1. **모든 권한 규칙은 Spring 에 있다.** 화면에서 버튼을 숨기는 것으로 권한을 대신하지 않는다.
2. **중앙 판단.** 모든 쓰기와 민감 조회는 `common/security/AccessPolicy` 의 `require(actor, action, resource)` 를 거친다. 컨트롤러·서비스마다 역할을 `if` 로 가르는 코드를 새로 만들지 않는다.
3. **기본 거부.** 이 문서에 허용으로 적히지 않은 접근은 거부한다. 남의 리소스는 `NOT_FOUND`(존재를 노출하지 않는다), 역할·상태 때문에 못 하는 일은 `FORBIDDEN` 또는 `INVALID_STATE`.
4. **역할·상태는 요청마다 DB 기준.** JWT 클레임의 역할·user metadata 를 권한 판단에 쓰지 않는다. 권한 판단용 Actor 는 캐시하지 않는다(요청당 PK 조회 1회 — 정지·역할 변경이 다음 요청부터 반영).
5. **보호 필드는 전용 서비스 메서드로만 바꾼다.** 역할·상태·소속 권역·담당 권역·배정 매니저·금액·평점·완료 건수를 클라이언트 값으로 갱신하는 범용 update API 를 두지 않는다.
6. **권한 상승 방지.** 누구도 자기 자신의 역할·상태·소속 권역·담당 권역을 바꿀 수 없다. 가입 시 역할은 서버가 정한다(매니저 앱 가입 = `manager` + `pending`).
7. **민감 작업은 업무 처리와 활동 이력 기록을 같은 트랜잭션에서** 한다(§11).
8. **파일은 Spring 이 권한을 확인한 뒤 짧은 서명 URL 로만** 준다. 비공개 버킷만 쓴다.
9. **RLS 는 안전망.** 앱은 Supabase 데이터·Storage 를 직접 부르지 않는다(고객 앱의 Supabase 호출은 Auth 소셜 로그인뿐). 모든 public 표는 RLS 켬 + 정책 0개 + anon·authenticated 권한 없음(§13).

## 2. 역할

한 사용자는 역할 하나. `profiles.role` ∈ `customer` · `manager` · `regional_manager` · `admin`.

| 역할 | 하는 일 |
|---|---|
| `admin` | 전체 운영. 사람·돈·규칙을 바꾼다. **1명.** 앱에 임명·해임 기능 없음 — 개발자가 DB 에서 직접 지정·해제 |
| `regional_manager` | 담당 권역의 현장 운영 + **일반 매니저 업무 전부**(역할 상속: 콜 수신·수락, 반납, 청소 기록, 사진, 본인 정산) |
| `manager` | 배정된 청소 수행 |
| `customer` | 청소 예약·이용 |

### 2.1 어드민 보호
- 어드민 API(`/api/v1/admin/**`) 는 **JWT `aal` = `aal2`(MFA 통과 세션)** 에서만 허용한다. `aal1` 이면 403.
- 어드민은 본인의 역할·상태를 바꿀 수 없다. 마지막 남은 어드민은 강등·정지·퇴사 처리할 수 없다.
- 공용 비밀값 `X-Admin-Token`(`ADMIN_TOKEN`) 방식은 **폐지**한다(§15-4). 기존 관리자 API 5개(작업 강제 완료·바디캠 등록·재매칭·패널티 면제·문의 답변)는 admin 역할 + aal2 로 옮긴다.
- 어드민 화면은 **매니저 앱 안의 배너 관리·공지 관리만**(§15-20, 2026-11-12). 어드민이 매니저 앱에 로그인하면 인증앱 6자리(MFA)를 한 번 더 받아 aal2 세션을 만들고, 매니저 탭 대신 관리자 홈으로 간다(어드민은 매니저 업무를 하지 않는다). 그 밖의 어드민 기능은 지금처럼 Supabase 계정(MFA 등록)으로 받은 JWT 로 API 를 직접 부른다. 계정 준비 절차는 `runbook.md`.

## 3. 매니저 계정 상태

`manager_profiles.status` ∈ `pending`(승인 대기) · `active`(활동 중) · `suspended`(활동 정지) · `dormant`(휴면) · `withdrawn`(퇴사). 매니저와 지역 매니저 모두 적용.

| | pending | active | suspended | dormant | withdrawn |
|---|---|---|---|---|---|
| 로그인 | O | O | O | O | O (정산 조회 목적, 기간 한정) |
| 본인 프로필 조회 | O | O | O | O | 이름 등 최소 정보 |
| 본인 프로필 수정 | O (가입 서류 보완) | O | X | O | X |
| 공지 열람 | X | O | O | O | X |
| 과거 예약·작업 이력 | - | O | O | O | X |
| 콜 수신·수락 | X | O | X | X | X |
| 청소 기록·사진 업로드 | X | O | X | X | X |
| 본인 정산 조회 | X | O | O | O | O (마지막 정산 지급 후 3개월) |
| 지역 매니저 관리 권한 | X | O | X | X | X |

- **업무 수행은 `active` 에서만.** 작업 시작·일시정지·재개·완료, 사진, 라이브 송출 진입부에서 검사한다.
- **모든 상태 전환은 어드민만.** 매니저는 어떤 경우에도 자신의 상태를 바꿀 수 없다. 휴면 요청은 문의로 받아 어드민이 처리한다.
- **매니저 본인 탈퇴 API 는 막는다**(§15-6). 매니저 앱의 탈퇴는 "퇴사 요청"(문의) 안내로 바꾸고, 어드민이 `withdrawn` 으로 전환한다. 퇴사는 소프트 삭제다(계정·Supabase 사용자 유지). 정산 조회 기간이 끝난 뒤의 최종 파기는 별도 절차.
- 퇴사자 접근 기한 = `max(마지막 정산 지급 시각 settlements.settled_at, 퇴사 시각) + 3개월`(`app_settings`, §12). 요청 시점에 계산한다(스케줄러에 의존하지 않음). 퇴사자는 정산 화면만 쓴다.
- 신규 가입 매니저는 서버가 `manager` + `pending` 으로 만든다. 소속 권역은 `pending` 동안만 비어 있을 수 있고 승인 때 어드민이 지정한다(§15-11).
- **정지·휴면·퇴사로 전환할 때 이미 배정된 예약:** 시작 전(`scheduled`) 예약은 같은 트랜잭션에서 배정을 풀고 다음 회차 콜로 다시 매칭한다(활동 이력 기록). 진행 중(`in_progress`·`paused`) 작업이 있으면 전환을 거부한다 — 완료(또는 어드민 완료) 뒤 전환.

### 3.1 패널티 "콜 배정 정지" 와의 관계 (§15-1)
- 기존 패널티 자동 정지(`manager_profiles.suspended_until`, 점수 5점 7일·8점 30일)는 **계정 상태와 별개인 "콜 수신 제한"** 으로 유지한다. 계정 상태는 `active` 그대로이고, 제한 기간에는 새 콜만 받지 못한다(이미 수락한 방문은 진행).
- 계정 상태 `suspended` 는 어드민만 전환하며 업무 전면 금지다.

## 4. 역할별 권한

### 4.1 admin
- 전체 매니저 조회·관리. 역할 부여·변경·회수(어드민 역할 제외 — DB 에서만).
- 지역 매니저 담당 권역 지정·변경·회수, 매니저 소속 권역 변경.
- 모든 계정 상태 전환(승인·정지·해제·휴면 전환·복귀·퇴사).
- 전국 예약 조회·취소·재배정. 전체 고객 피드백·문의 조회·처리.
- 공지 등록·수정·삭제. 권역별 운영 현황 조회.
- 정산·보너스·페널티 관리(부과·면제), 정산 계좌 변경 요청 처리.
- 활동 이력 조회. 설정값(`app_settings`) 변경.
- 사진 교체 이력 조회(어드민만).

### 4.2 regional_manager (담당 권역 한정, `active` 일 때만)
- 담당 권역 소속 매니저 조회 — 운영·실적 정보만(§7.3).
- 담당 권역 예약 조회·취소·재배정.
- 담당 권역 고객 피드백 조회, 고객 문의 접수·처리.
- 담당 권역 예약의 고객 정보 조회(§7.4).
- 일반 매니저 업무 전부.

### 4.3 manager
- 본인 프로필 조회, 허용된 정보 수정(§7.5).
- 본인에게 온 콜 조회·수락·거절. 본인 배정 예약 조회, 본인 일정 확인.
- 청소 시작·완료 등 상태 기록. 전후 사진·작업 결과 업로드.
- 본인 담당 예약의 고객 요청사항 확인. 본인 수입·정산 조회.

### 4.4 customer
- 본인 프로필·주소·주거 정보 관리. 예약·정기예약 신청, 본인 예약 조회·취소(기존 취소 정책 유지).
- 결제수단 관리, 본인 결제·환불 조회. 배정 매니저의 공개 정보 확인(§7.6).
- 완료된 청소의 사진(최신본)·녹화본 열람(§8). 피드백 작성(§9).
- 문의 작성·본인 문의 조회. 알림 설정, 공지·FAQ 열람.
- 본인 예약의 출입 정보 입력·수정(§7.2).

### 4.5 직무 분리 (지역 매니저가 직접 청소하는 경우)
- 지역 매니저 **본인이 수행하는 예약**의 피드백·고객 문의·취소·재배정은 **어드민만** 처리한다.
- 지역 매니저는 재배정 권한으로 **본인에게** 예약을 배정할 수 없다. 콜로만 수락한다.
- 지역 매니저 본인의 평점·피드백은 본인이 볼 수 없다.
- 본인 수행 예약의 고객 정보·출입 정보는 매니저 규칙을 따른다.

## 5. 권역

- 표: 권역(`regions`), 시·군·구 → 권역 매핑(`region_sigungu`, '시도 + 시군구' 당 권역 하나), 지역 매니저 ↔ 권역(`regional_manager_regions`, 여러 권역 가능, 운영 원칙은 1인 1권역).
- **소속 권역:** 매니저·지역 매니저는 관리용 소속 권역(`manager_profiles.home_region_id`)을 정확히 하나 가진다(`pending` 만 예외). 기존 `areas`(매칭용 활동 지역)는 유지하되 **소속 권역에 매핑된 시·군·구만** 허용한다.
- **예약 권역 스냅샷:** 예약 생성 때 `bookings.region_id` 를 저장한다. 조회 범위는 매니저의 현재 소속이 아니라 **예약의 권역**이 기준이다.
- **매핑이 없는 시·군·구의 예약은 거절한다**("아직 서비스하지 않는 지역", §15-12).
- 초기 권역 목록은 마이그레이션이 아니라 어드민 API 로 등록한다(§15-10).

## 6. 배정·반납·취소·재배정

### 6.1 배정 (지정 콜 유지)
- 기존 `offers` 기반 지정 콜을 유지한다. **콜은 예약 권역에 소속된 `active` 매니저에게만** 보낸다(우선 오퍼 포함). 콜 수신 제한(§3.1) 중이면 제외.
- 콜을 받은 매니저만 그 예약의 수락 전 공개 정보(§7.1-a)를 본다.
- 수락은 "예약이 아직 미배정이고 이 매니저에게 유효한 콜이 있을 때만" 원자적으로 처리한다(매니저 → 예약 → 오퍼 행 잠금 + `offers_one_accepted` 유니크 + 겹침 배타 제약 — 기존 구조 유지).

### 6.2 반납 (§15-5)
- 매니저는 **청소 시작 72시간 전까지** 수락한 예약을 직접 반납할 수 있다. 반납하면 다음 회차 콜을 보낸다. **점수 0점**(자동 페널티 없음).
- 72시간 이후에는 직접 반납할 수 없고 어드민 또는 지역 매니저(담당 권역, 직무 분리 적용)에게 요청한다 → 운영자 반납 API. 페널티 부과 여부는 어드민이 판단한다(어드민 페널티 부과 API).
- **모든 반납은 기한 안팎과 상관없이 활동 이력에 기록**한다.
- 지각·미방문 점수와 패널티 누적 정지 규칙은 그대로 둔다(`manager-policy.md`). 기존 "24시간 전 월 2회 무료·이후 1점 / 24~4시간 1점" 방문 취소 점수는 폐지된다.

### 6.3 예약 상태 전이 (역할별)
| 전이 | 허용 |
|---|---|
| requested → assigning | 시스템 |
| assigning → scheduled | 콜을 받은 `active` 매니저·지역 매니저(수락) |
| scheduled → assigning (반납) | 배정 매니저(72시간 전까지) / 어드민 / 지역 매니저(담당 권역, 본인 수행 예약 제외) |
| scheduled → in_progress | 배정된 `active` 매니저(당일) |
| in_progress ⇄ paused | 배정된 `active` 매니저 |
| in_progress·paused → done | 배정된 `active` 매니저 / 어드민 |
| requested·assigning·scheduled → cancelled | 고객(기존 기한) / 어드민(전국) / 지역 매니저(담당 권역, 본인 수행 예약 제외) / 시스템 |
| 재배정(배정 매니저 교체 또는 직접 배정) | 어드민 / 지역 매니저(담당 권역, 본인 수행 예약 제외, 본인에게 배정 금지) |

- 운영자 취소는 **시작 전 예약만**, 고객에게 **전액 환불**한다(§15-13).
- 재배정 대상은 예약 권역에 소속된 `active` 매니저여야 한다. 이전 매니저의 수락 오퍼는 `superseded`.
- **재배정 즉시 이전 매니저는 그 예약의 민감 정보·출입 정보에 접근할 수 없다** — 매 요청마다 "지금 배정된 매니저인가" 를 확인한다.

## 7. 정보 공개

### 7.1 예약 정보의 세 단계
| 단계 | 내용 | 볼 수 있는 사람 |
|---|---|---|
| (a) 기본 정보 | 날짜·시간, 동 단위 위치, 서비스 유형·주거 형태·평수, 매니저 수령 예정 금액, 정형 요청사항(반려동물, 현장 안내 칩, 옵션) | 콜을 받은 매니저(수락 전), 배정 매니저, 권한 있는 운영자 |
| (b) 민감 정보 | 고객 이름·연락처, 상세 주소, **자유 입력 메모** | 지금 배정된 매니저, 지역 매니저(담당 권역), 어드민 |
| (c) 출입 정보 | 공동현관 비밀번호, 도어락 번호, 열쇠 위치 등(전용 저장소) | §7.2 시간 규칙 |

- 자유 메모와 수리 증상 상세는 (b) 다. 수락 전 콜 화면에 나오지 않는다.

### 7.2 출입 정보 시간 규칙
- **배정 매니저:** 청소 시작 예정 2시간 전부터 완료 기록 전까지. 완료를 기록하지 않아도 종료 예정 시각 6시간 후에는 숨긴다.
- **지역 매니저:** 담당 권역 예약에 한해 **청소 당일(서울 0시~24시)** 에만. 본인 수행 예약은 매니저 규칙.
- **어드민:** 기본 화면에 노출하지 않는다. 열람 시 사유 입력을 요구하고 사유와 열람 기록을 활동 이력에 남긴다(활동 이력 "변경만 기록" 원칙의 유일한 예외).
- **고객:** 본인 예약의 출입 정보 입력·수정.
- 저장은 분리된 표 + 접근 통제. 컬럼 암호화는 이번 범위 밖(§15-15).

### 7.3 매니저 정보
- 운영·실적 정보: 이름, 연락처, 상태, 일정, 완료 건수, 반납 이력, 평점, **보험 만료일, 교육 이수**(§15-14).
- 민감 정보: 정산 계좌(마스킹 값), 신원 확인·배경 조회·가입 서류, 주소 → **어드민과 매니저 본인만.**
- 지역 매니저: 담당 권역 소속 매니저의 운영·실적 정보. 본인 행에서는 평점 제외.

### 7.4 고객 정보
- 지역 매니저: 담당 권역 예약의 고객 이름·연락처, 상세 주소, 자유 메모, 출입 정보(§7.2). 본인 수행 예약은 매니저 규칙.
- 어드민: 전체(출입 정보는 §7.2).
- 매니저: §7.1 단계별.

### 7.5 매니저 본인 정보 수정
- 정산 계좌는 직접 수정할 수 없다. 변경 요청 → 어드민 확인 후 반영 → 매니저 본인에게 알림.
- 역할·상태·소속 권역·평점·완료 건수는 본인이 수정할 수 없다.
- 연락처, 프로필 사진·자기소개, 주소의 직접 수정 허용 여부는 **미정**이다. 지금은 해당 수정 API 가 없다(읽기만). 결정 전까지 만들지 않는다.

### 7.6 고객에게 공개하는 매니저 정보
- 본인 예약에 배정된 매니저의 프로필 사진과 이름(전체)만, 배정 이후부터. 지난 예약에서도 유지.
- 평점·완료 건수·교육 이수·연락처는 공개하지 않는다. 직접 연락처 교환 없음.

## 8. 사진·녹화본

- 청소 전후 사진과 녹화본은 **어떤 역할도 삭제하거나 덮어쓸 수 없다.** `job-photos`·`recordings` 버킷에 Spring 이 remove·upsert(덮어쓰기)를 쓰지 않는다. 녹화 파일도 녹화마다 다른 경로에 쓴다.
- 다시 찍기는 **완료 기록 전까지만**, 항상 새 경로의 새 파일로 올린다. 이전 파일은 "교체됨" 으로 표시해 보관한다(사진 버전 표).
- **교체 이력은 어드민만** 본다. 그 밖의 역할에는 최신 파일만 보인다.
- **보존: 영구 보관**(§15-2). 90일 보존 정리와 탈퇴 시 파기에서 청소 사진·녹화본을 뺀다. (수리 예약 첨부 사진 `repair-photos` 는 이 규칙의 대상이 아니다.)
- 고객은 본인 예약의 **완료(`done`) 이후** 전후 사진(최신본)과 녹화본을 열람한다.
- 실시간 영상(LiveKit) 기능 자체는 이번 범위 밖이다.
- 녹화본의 목적 외 활용(AI 학습, `recording_segments` 학습 검토 포함)은 **고객과 매니저가 각각 동의한 경우에만** 허용한다 — 동의 기록 구조(`media_consents`)로 확인한다.

## 9. 고객 피드백

- 작성: 고객 본인 예약, 완료 후 7일 이내, 예약당 1건.
- 수정: 작성 후 24시간 이내, 이전 내용은 수정 이력 표에 보관. 삭제 불가.
- 열람: 어드민 전체, 지역 매니저 담당 권역(본인 수행 예약 제외). 매니저는 피드백과 평점을 볼 수 없다.
- 평점(`manager_profiles.rating`)은 피드백 평균으로 다시 계산한다(§15-16).

## 10. 공지·문의

- 공지 등록·수정·삭제는 어드민만. 대상 권역(`notices.region_id`, 없으면 전체)을 지정할 수 있다. 수정·삭제는 활동 이력에 기록.
- 매니저는 전체 공지 + 소속 권역 공지, 지역 매니저는 전체 공지 + 담당 권역 공지를 본다(§3 표의 상태 제한). 매니저 공지는 로그인이 필요하다. 고객 대상 공지는 기존 `audience` 규칙 유지.
- 문의에 예약(`inquiries.booking_id`)과 권역(`inquiries.region_id`)을 연결한다. 권역이 있는 문의는 담당 지역 매니저가 처리할 수 있고, 권역이 없거나 지역 매니저 본인 수행 예약의 문의는 어드민만.

## 11. 활동 이력

- 범용 표 `activity_logs`: 행위자(없으면 시스템), 행위자 역할, 행위, 대상 종류·id, 변경 전·후(jsonb), 사유, 시각.
- 기록 대상: 역할·상태 변경, 소속·담당 권역 변경, 콜 수락·반납, 예약 취소·재배정, 계좌 변경 반영, 정산·보너스·페널티 처리, 공지 수정·삭제, 사진 교체, 설정값 변경, 어드민의 출입 정보 열람.
- 조회는 어드민만. **누구도 수정·삭제할 수 없다** — 애플리케이션 계정 포함. 방법(§15-17): 앱 전용 DB 계정(표 소유자 아님, RLS 우회 없음, 활동 이력에 INSERT·SELECT 만) + UPDATE·DELETE·TRUNCATE 를 막는 트리거. Flyway 는 지금처럼 소유자 계정으로 접속한다.
- 민감 작업은 업무 처리와 이력 기록을 같은 트랜잭션에서 한다.

## 13. DB 보호

- 모든 public 표: RLS 켬, 정책 0개, anon·authenticated 권한 없음. 새 표는 만드는 마이그레이션에서 RLS 를 켠다.
- public 스키마의 **기본 권한(default privileges)** 에서 anon·authenticated 를 뺀다 — 새 표·시퀀스·함수가 앱 키에 자동으로 열리지 않게(§15-7).
- `flyway_schema_history` 는 RLS 를 켜지 않는다(Flyway 가 자기 잠금과 엉켜 기동이 실패한다, V011 주석). 대신 anon·authenticated 권한을 회수해 둔다.
- V064 이후 Flyway 계정이 만드는 표·시퀀스·함수는 anon·authenticated(함수는 PUBLIC 포함)에 자동으로 열리지 않는다. 그래도 새 표를 만드는 마이그레이션은 RLS 를 직접 켠다(안전망 두 겹).
- 앱(Spring) 은 앱 전용 DB 계정, Flyway 는 표 소유자 계정으로 접속한다(§11).

## 15. 결정 기록

- **2026-11-12 원본 요구사항** — 위 §1~§13 의 결정 사항 전부(원본 문서 2~6장).
- **2026-11-12 1단계 질의응답(사용자 답)**
  1. 패널티 "콜 배정 정지" 와 계정 상태 `suspended` 는 **분리**(§3.1).
  2. 청소 사진·녹화본은 시스템 보존 정리·탈퇴 파기도 하지 않고 **영구 보관**(§8). 약관·개인정보 처리방침의 보관 기간 문구 변경과 법률 검토가 필요하다(결과 보고에 명시).
  3. 어드민은 **API 만**, 화면은 나중.
  4. `X-Admin-Token` 은 **폐지**하고 역할 방식만.
  5. 72시간 전 직접 반납은 **0점**, 이후는 운영자 처리·어드민 판단.
  6. 매니저 **본인 탈퇴 차단**, 퇴사로만.
  7. `flyway_schema_history` 는 RLS 대신 **권한 회수 방식**(+ 기본 권한 회수).
  8. 녹화본은 결정대로 완료 후에만 고객에게 공개.
- **2026-11-12 2단계 계획 승인(제안대로)**
  10. 권역 초기 데이터는 어드민 API 로 등록(마이그레이션은 빈 표).
  11. `pending` 만 소속 권역 null 허용, 승인 때 지정.
  12. 매핑 없는 시·군·구 예약은 거절.
  13. 운영자 취소는 시작 전 예약만, 전액 환불.
  14. 보험 만료일·교육 이수는 운영 정보(지역 매니저 열람 가능, 고객 비공개).
  15. 출입 정보는 분리 표 + 접근 통제, 암호화는 범위 밖.
  16. 평점 = 피드백 평균.
  17. 활동 이력 불변은 앱 전용 DB 계정 분리 + 트리거(인프라 변경 승인: 새 DB 계정 비밀번호, Cloud Run 시크릿).
  18. Docker 가 없는 컴퓨터에서는 통합 테스트를 백엔드 컴퓨터에서 돌리거나 PGlite 로 대신 검증하고, 못 돌린 것은 "IT 미실행" 으로 기록.
  19. 어드민 계정 준비(Supabase 계정 생성 → DB 에서 role=admin → TOTP MFA 등록, 대시보드 MFA 켜기)는 개발자가 하고 `runbook.md` 에 절차를 적는다.
- **2026-11-12 3단계 — 배너·공지 관리 화면 (사용자 요청 "매니저 앱에서 관리자가 배너 이미지·공지를 올리면 고객 앱에 반영")**
  20. §15-3 을 일부 바꾼다: 어드민 화면을 **매니저 앱 안에** 둔다. 범위는 고객 앱 홈 혜택 배너 관리와 공지 관리뿐. 로그인은 매니저 앱 비밀번호 로그인 + 인증앱 6자리(aal2) — MFA 필수는 그대로.
  21. 순서: R2(역할) → R4(Actor·AccessPolicy·aal2) → 어드민 MFA 로그인 + R3(활동 이력) → 공지 관리(R16 의 어드민 공지 API 중 대상 선택·등록·수정·삭제. 권역 지정은 R5 뒤) → 배너 관리.
  22. 배너: 이미지 + 대체 문구(제목·설명) + **게시 기간**(시작·종료) + **순서 변경**. 켜기·끄기 스위치와 누르면 이동은 두지 않는다. 이미지는 비공개 버킷 + Spring 이 주는 서명 URL(§1-8).
  23. 공지 최신화: 고객 앱은 지금처럼 화면을 열 때마다 서버에서 다시 받는다(새 공지 표시·푸시 없음). 공지 대상은 고객·매니저·전체 중 선택, 등록·수정·삭제, 수정·삭제는 활동 이력에 기록.
  24. 어드민은 매니저 업무(콜·일정·정산)를 하지 않는다 — 매니저 앱에서 매니저 탭 대신 관리자 홈만 본다.

- 녹화본에 매니저의 음성 등이 포함되어 고객에게 공개된다는 점을 **매니저 안내·약관에 반영**해야 한다.
- 사진·녹화본 영구 보관에 맞춰 약관·개인정보 처리방침의 보관 기간 문구를 바꾸고 법률 검토를 받아야 한다.
- 매니저 앱 문구 변경(반납 기한, 탈퇴 → 퇴사 요청, 공지 로그인)은 Figma 에 없어 "코드에서 정함" 으로 기록한다.
